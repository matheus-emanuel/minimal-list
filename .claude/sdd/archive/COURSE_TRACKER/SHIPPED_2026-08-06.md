## Summary

Course Tracker turns a personal, static markdown checklist of free certifications (Databricks, SQL, Oracle Cloud, Scrum) into a public web app: anyone can browse the curated course list, but only logged-in users can mark individual courses as completed, with progress persisted per account. A `sysadmin` role manages the course catalog (create/edit/remove) without touching code, and a shared badge wall lets logged-in users post photos of earned certifications, like each other's posts, and report inappropriate content for the sysadmin to review. Built on Next.js (App Router) + Supabase (Postgres, Auth, Storage) + Vercel, entirely on free tiers, with every access rule enforced at the database level via Row-Level Security — not just in application code. The app is live-deployed against a real Supabase project (`lista-minima`), migrated, seeded with the original 24 courses, and smoke-tested end-to-end.

## Lessons Learned

### Process

- Running the full BRAINSTORM → DEFINE → DESIGN → BUILD chain in one sitting, with incremental validation checkpoints during BRAINSTORM (stack choice, data model, scope cuts confirmed one at a time), meant DESIGN needed zero clarifying questions — the discovery work upfront paid for itself.
- The DEFINE phase's "quantify success criteria yourself, mark as Assumptions" approach (rather than blocking on the user for numbers like upload limits or Lighthouse targets) kept momentum without sacrificing traceability — every guessed number was labeled and later spot-checked.
- Treating `/build` as truly autonomous (logging decision forks instead of asking) worked well for implementation-level choices, but the *value* of the build jumped sharply once real infrastructure (Docker, a linked Supabase project) became available mid-session — static verification (tsc, lint, `next build`) is necessary but not sufficient for a database-security-heavy feature.

### Technical

- **RLS policies alone are not enough.** Postgres requires a base `GRANT` on a table before RLS policies are even evaluated — this is easy to miss because `profiles` (built first, per Decision 2's column-level `GRANT` requirement) happened to get it right, while the other 5 tables silently relied on RLS alone and failed with `42501 permission denied` for every role, `service_role` included, the moment they were tested against a real database. This is now called out explicitly in DESIGN's Security Considerations for future features.
- Pinning exact dependency versions in a DESIGN doc's code patterns (e.g. `@supabase/ssr@0.5.2`) can silently rot: `npm install` resolved `@supabase/supabase-js` to a much newer `2.112.x` via a loose `^2.47.0` range, and the older `@supabase/ssr` imported from a module path that no longer existed in that version — a real version-skew bug caught only by actually running `tsc --noEmit`, not by reading the code.
- Local Supabase (`supabase start`) is genuinely valuable for catching this class of bug for free, but Docker Desktop's WSL2 port-forwarding proxy was flaky on first use — disabling non-essential services (`analytics`, `studio`, `inbucket`) and moving 2 ports resolved it in a few minutes once recognized as an infra quirk, not a real port conflict.
- `supabase gen types typescript --linked` against a real project is worth running even after hand-authoring types to unblock early type-checking — it catches shape drift (e.g. the `__InternalSupabase`/`Relationships` fields current `supabase-js` requires) that's easy to get subtly wrong by hand.

### Communication

- Asking one targeted question at a time during BRAINSTORM (public vs. closed signup, auth method, badge feed shape, moderation level) surfaced real constraints — e.g. the user explicitly confirming "básico: limite + denúncia" over "aprovação prévia" directly shaped the moderation architecture and avoided building an unwanted approval-queue UI.
- The mid-build handoff ("ativei o docker e linkei o Supabase... pode seguir como preferir") was a clean, low-friction way for the user to unblock infrastructure without needing to specify exact next steps — worth defaulting to "run the real verification now that it's possible" rather than re-asking what to do.

### Tools & Libraries

- **Zod + Server Actions** made the "RLS is the real boundary, app validation is just UX" split clean: every mutation validates shape with Zod, then lets Postgres's RLS be the actual authorization decision — no duplicated authorization logic in TypeScript.
- **Supabase CLI local dev stack** (`supabase start`, `db reset`, `migration list`, `db push --include-seed`) covered the entire local → remote migration lifecycle without any custom tooling, and its Vitest-based RLS testing pattern (real users via the Admin API, `SECURITY DEFINER` promotion, cleanup in `afterAll`) is directly reusable for the next feature.

## Recommendations for Future Work

| Area | Recommendation |
|------|-----------------|
| Deployment | Deploy to Vercel, then run Lighthouse against the real edge-hosted URL to close out the two pending performance success criteria |
| E2E coverage | Add the two binary image fixtures and seed a test user + sysadmin account, then run `npm run test:e2e` for full browser-level coverage of all 7 acceptance tests |
| Schema hygiene | For every future migration, explicitly pair each `ENABLE ROW LEVEL SECURITY` with the matching base `GRANT` statements in the same PR — add this as a one-line checklist item in the DESIGN template's Security Considerations section |
| CI | Add a GitHub Actions workflow that runs `supabase start` + the RLS suite on every PR touching `supabase/migrations/` — this would have caught the missing-`GRANT` bug automatically instead of requiring a manual live-infra pass |
| Content | Sysadmin should add the 10 "Certificações para Pesquisar e Adicionar" courses (Microsoft Learn, Snowflake, Kafka, etc.) via `/admin` once real URLs are found — intentionally left out of the seed |
